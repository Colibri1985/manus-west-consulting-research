# 1. Назначение и границы продукта
Создать воспроизводимый аналог переданного конструктора: простая форма подготовки бюджета движения денежных средств объекта для управляющих БЦ/ЖК и инженеров. Руководитель УК должен быстро проверить суммы, состав работ, материалы, ФОТ и расшифровку. БИТ.Финанс остаётся основной бюджетной системой.
Приложение обязано работать одним HTML-файлом локально в современном браузере, без сервера, установки, интернета, CDN, внешних библиотек и отправки данных во внешние сервисы. Исходники разработчика и тесты можно организовать модульно; результат сборки — один автономный HTML. Сервер для разработки не является зависимостью конечного продукта.
Один проект — один бюджет в открытой форме. Основной рабочий формат — JSON; XLSX/CSV — отчёты и загрузочные документы, не рабочая база. Многопользовательское редактирование и авторизация не требуются.

# 2. Иерархия источников и правила интерпретации
Приоритет: явные решения заказчика и это ТЗ → фактический исходный HTML для совместимости → неповреждённая исходная форма БИТ для конкретного документа → автоматизированные тесты → предположения разработчика.
Термины в ТЗ:
- «Как есть»: описание существующего поведения, полезное для воспроизведения и сравнения.
- «Обязательно»: целевое требование приёмки.
- «Известный дефект»: не переносить молча, оформить исправление и показать изменение результатов.
- «Внешняя приёмка»: проверка, которую нельзя подтвердить только HTML/Excel-парсером.
Не копировать известные ошибки ради побайтового совпадения. Любое отступление от исходных расчётов зафиксировать до изменения контрольных результатов. Не менять методологию по собственному усмотрению.
Файл содержит 115 статей и 160 деклараций функций; это признаки проверенной версии, а не ограничения будущей внутренней архитектуры. Точная структура, справочник и исходные значения приведены в reference_contract.json.

# 6. Шапка бюджета и период
Поля: проект/объект, ЦФО, periodStart, periodEnd, unit (RUB/K), openingBalance (число или null).
Значения источника по умолчанию: проект пустой; ЦФО «Управление коммерческой недвижимостью»; 01.01.2027–31.12.2027; RUB; начальный остаток null.
Поддерживается один календарный год, включая его неполный диапазон месяцев. Проверять валидность ISO-дат, начало ≤ окончание, одинаковый год. При ошибке не создавать ложный годовой итог. Неполный период разрешён для внутреннего анализа и отчётного XLSX; БИТ-выгрузка разрешена только за 01.01–31.12 одного года.
Это месячная, не дневная модель: если начало/конец внутри месяца, в исходнике выбираются затронутые месяцы целиком, без пропорции дням. Обязательно явно подписать это; не внедрять скрытый дневной перерасчёт. При необходимости предложить пользователю границы полных месяцев.
Каждая исходная позиция хранит свои startMonth/endMonth 1–12. Денежный итог = пересечение диапазона позиции с месяцами бюджета. В таблицах различать «Исходные месяцы» и «Итого за период».
Все хранимые и выгружаемые денежные значения — рубли. K влияет только на отображение денежных колонок. Количество, доля %, единицы, МРОТ и налоговые лимиты не делятся на 1000. Расшифровка ШР всегда в рублях.
Начальный остаток = остаток на начало выбранного периода. При null не показывать выдуманный нулевой остаток: накопленные и конечный остатки — прочерк. При числе, в том числе 0, closing = openingBalance + inflow − outflow.

# 8. Справочник статей
Воспроизвести полный исходный справочник из reference_contract.json, initialState.articles. Коды хранить строками. Не восстанавливать названия по памяти и не заменять сокращения произвольно.
Группы — узлы с детьми, листовые статьи — без детей. Прямой ввод разрешён только на допустимые листья. Групповые суммы — сумма собственного и дочерних потоков по правилам исходника; собственный ввод в группу не допускается.
Операции: создание, редактирование, удаление, активация/деактивация. При редактировании ID сохраняется. Запретить самородительство, циклы любой длины и ссылку на отсутствующего родителя. Все обходы должны быть защищены от циклов, включая импортируемое дерево.
Удаление запрещено при дочерних статьях, ссылках из доходов/расходов и назначении в персонале. При деактивации используемой статьи запросить подтверждение; связанные позиции не должны продолжать считаться незаметно.
Коды должны быть уникальны. Используемая статья без кода — ошибка, неиспользуемая без кода — предупреждение. Пользовательские статьи допустимы во внутреннем бюджете, но ненулевые суммы вне поддерживаемого шаблона БИТ блокируют БИТ-выгрузку, а не молча теряются.

# 9. Доходы
Разделы и области выбора: exploitation → 701.100; utilities → 701.300; additional → 701.200; capex → 701.400. Выбор ограничивается активными листовыми статьями соответствующего поддерева. Дополнительно контролировать направление in, в том числе после правок справочника.
Поля: раздел, статья, база, месячный тариф без НДС, ставка НДС, начало/окончание месяцев, описание услуги.
Ставки в исходнике: 22, 10, 7, 5, none («Без НДС»). Это допустимые параметры приложения, не заключение о применимости к конкретной операции.
Формулы: net = round2(base × tariff); vat = round2(net × rate/100), при none — 0; gross = round2(net + vat). На каждый месяц пересечения создать положительный денежный поток gross.
База и тариф конечные, неотрицательные. Нулевые значения разрешены. Отрицательные и нечисловые — ошибка. «Пустое» нельзя бесконтрольно превращать в корректный ноль; политика обязательных полей должна быть явной.
CRUD: сохранить новую, изменить с тем же ID, удалить с подтверждением, сбросить форму. Повторный пересчёт не создаёт дублей. При редактировании восстанавливаются все поля, включая НДС и месяцы.
Автоматические расходы КУ не создавать. Автоматическую наценку допуслуг в этом релизе не добавлять.

# 10. Работы, услуги, платежи и материалы
Типы: service «Работа / услуга»; material «Материал / закупка»; payment «Платёж / прочее». По умолчанию service.
Основные поля: статья выплаты, полная сумма с НДС в месяц, ставка НДС, месяцы, контрагент, договор, комментарий, описание материала до 2000 символов.
Материальные поля: обязательная номенклатура; необязательные единица, количество и цена. Ручная итоговая сумма остаётся главным денежным параметром. Если количество × цена отличается от суммы больше чем на 0,01 руб., выдавать предупреждение, а не молча менять сумму.
Формулы: gross = round2(amount); vat = round2(gross × rate/(100+rate)); net = round2(gross−vat). При none vat=0. Денежный поток = −gross за каждый месяц внутри бюджета.
Даже если название вкладки «Работы и платежи», ежедневных актов/дат оплаты в текущей модели нет: это повторяющаяся месячная сумма. Разовая закупка задаётся одинаковыми месяцами начала и окончания. Не умножать количество материала на сумму повторно.
Материал и услуга одной статьи — разные исходные записи, нельзя объединять при сохранении. В итоговой матрице они суммируются по статье.
Проверять неотрицательные конечные суммы/количества/цены, месяцы, активную листовую статью direction=out, существующие связи. Неизвестный тип/ставка не должны проходить как неявное значение по умолчанию.
Не обрезать описание незаметно: использовать ограничение ввода/счётчик либо понятное предупреждение. Существующее содержимое JSON не терять при редактировании.

# 11. Реестр материалов
Отдельная вкладка и общий источник данных для HTML, CSV и листа XLSX. Брать корректные рассчитанные материальные позиции и раскрывать по каждому месяцу пересечения, не по всему исходному диапазону.
Колонки в порядке источника: месяц; статья; код; номенклатура; единица; количество; цена; сумма с НДС; НДС; сумма без НДС; ставка; контрагент; договор; описание материала; комментарий.
Повтор одной номенклатуры в нескольких месяцах допустим. Количество в каждой строке трактуется как количество данной месячной закупки, а не как годовой итог; подписать это для диапазонных закупок.
CSV: UTF-8 BOM, разделитель «;», CRLF, поля в кавычках, внутренние кавычки удваиваются. Не позволять пользовательским комментариям исполняться как Excel-формулы при открытии CSV; применять безопасное представление текстовых полей.
Для MVP достаточно детального выгружаемого реестра; браузерные сводные таблицы и складские движения не обязательны.

# 12. Налоговый профиль: параметры, а не юридическое заключение
Показывать редактируемый профиль: общий/МСП, вид МСП, травматизм, таблица годов, шкала НДФЛ, назначение статей.
В исходнике по умолчанию для 2026 и 2027: mrot=27093, epvb=2979000; injuryRate=0.2; isMSP=false. Это наследуемые технические значения, не подтверждённые нормативы 2027 года. Не выдавать их за актуальные обязательные нормы. Изменение значения в UI должно пересчитывать бюджет без изменения HTML и сохраняться в JSON.
МРОТ 28935 обсуждался заказчиком как значение для планирования; автоматически не подменять сохранённые профили. Актуализацию параметров и изменение исходных дефолтов согласовать отдельно.
Для года бюджета сначала искать ровно одну точную строку; дубли годов — ошибка. Если точной нет, исходник использует последний предшествующий год, затем первый доступный/дефолт; показывать использованный год и предупреждение. Не выдавать fallback за подтверждённый параметр.
Шкала источника: 13% до 2400000; 15% до 5000000; 18% до 20000000; 20% до 50000000; 22% выше. Верхние пределы строго возрастают, последняя ступень открытая, ставки 0≤rate<100. Не нормализовать повреждённую шкалу незаметным удалением строк.
Режим взносов источника: general — 30% до годовой ЕПВБ на одну единицу и 15,1% сверх; msp — 30% до 1,5 МРОТ в месяц, 15% сверх; msp_manufacturing — 30% до 1,5 МРОТ, 7,6% сверх. Это контракт воспроизведения управленческой модели, не универсальный налоговый движок. Отдельную юридическую верификацию этих режимов не считать выполненной.
Травматизм = полный gross × injuryRate/100, без ограничения ЕПВБ. Вне 0–8,5% — сообщение проверки; отрицательное/нечисловое не включать в расчёт.

# 13. Мини-ШР и режимы ФОТ
Поля: должность; график 5/2, 2/2, 1/3, 1/2, 6/1, иной; units; allocation%; полная netPerUnit; премия февраль на единицу; премия август на единицу; месяцы работы.
График — аналитический текст, не рабочий календарь и не множитель зарплаты. Единицы могут быть дробными; доля 0–100%. Прогрессивная база рассчитывается на одну условную единицу, а не на сумму разных людей.
Три режима: staff_only (по умолчанию), manual_only, mixed. В первом ручные ФОТ-расходы 702.0101–702.0105 не участвуют; во втором мини-ШР не участвует; в mixed оба источника разрешены только после явного подтверждения контроля задвоения. Неподтверждённый mixed — ошибка независимо от наличия ручных строк.
Не удалять исключённые режимом записи. Показывать причину невключения. На обзоре отдельно мини-ШР, ручной ФОТ, сумма за период.
Назначение статей: salary=702.0101; bonus=702.0102; ndfl=702.0103; contrib=702.0104 по умолчанию. Пользователь может переназначить на активный лист выплаты. Изменение действует на все строки. Некорректное назначение блокирует расчёт персонала и финальные выгрузки.
Премии февраля/августа — согласованные отдельные выплаты: не входят в базу НДФЛ, страховых взносов и травматизма и не увеличивают накопленные базы. Они масштабируются на единицы и долю. Не исправлять это правило по собственной инициативе; отдельно обозначать как управленческую настройку.

# 14. Алгоритм персонала и доли объекта
Поле netPerUnit означает полную зарплату одной единицы на руки по компании. Полная налоговая база не уменьшается на долю объекта.
В каждом месяце работы одной единицы:
1. Получить fullNet = netPerUnit.
2. Восстановить fullGross из fullNet по прогрессивной шкале с fullGrossYtd до данного месяца.
3. fullNdfl = fullGross − fullNet; взносы и травматизм считать с fullGross и полной накопленной базы одной единицы.
4. Выбрать премию февраля/августа, не включая её в облагаемую базу.
5. Увеличить полные накопленные базы на fullGross независимо от принадлежности месяца горизонту бюджета.
6. Применить factor = units × allocation/100 только к готовым денежным результатам.
7. В бюджет/annual включить только месяцы пересечения с периодом. Остальные рассчитанные полные месяцы нужны для базы и пояснения.
Нельзя сначала умножить net на 50%, затем искать ступень налога; нельзя объединить доход двух работников в одну шкалу; нельзя начислить 15% на всю зарплату месяца только потому, что порог пересечён внутри него.
Gross-up: идти по ступеням, пропускать уже пройденные пределы без уменьшения позиции накопленного дохода. Для каждой ступени grossCapacity = upper−position; netCapacity = grossCapacity×(1−rate). Последовательно распределять net по доступным ступеням. Внутри месяца пересечения часть gross относится к нижней, часть к следующей ставке.
Начальные базы в источнике равны нулю на начало указанного периода работы строки. Источник не знает облагаемых доходов вне строки и не различает дату найма в УК и начало участия в объекте. Не выдумывать недостающие доходы. Добавление отдельных периодов или входных баз — только отдельным согласованным изменением.

# 15. Округление: совместимость и обязательное согласование
Как есть: round2 реализован через Math.round((Number(n)+Number.EPSILON)×100)/100. Это управленческий расчёт в копейках, не бухгалтерский расчёт удержанного НДФЛ по полным рублям.
Известный дефект №1: factor в источнике округляется до двух знаков до умножения. При доле 33,33% он превращается в 0,33. В целевой корректной модели не округлять промежуточный factor, округлять денежные суммы.
Известный дефект №2: gross, net, ndfl, insurance, injury и contributions округляются независимо. Показанная колонка СВ вычисляется как annual.contributions−annual.injury и может не совпасть с отдельно накопленным annual.insurance.
Обязательно принять явную политику: net и ndfl распределяются и округляются; gross объекта = net+ndfl; insurance и injury распределяются отдельно; contributions = insurance+injury; total = gross+contributions+bonus. Это устраняет копеечное рассогласование и изменит часть исторических итогов. Перед переключением представить заказчику таблицу «было/стало», не менять старые JSON молча.
Регрессионные fixtures в reference_contract.json фиксируют поведение исходника, включая расхождения. Они служат доказательством исходной версии, а не требованием воспроизвести дефект. Для режима исправлений создать отдельные ожидаемые результаты.
Не называть копеечный gross-up точным налоговым удержанием по НК РФ. Рублёвое округление НДФЛ и расчёт по датам фактических выплат — отдельное изменение методологии, не внедрять скрыто.

# 16. Расшифровка ШР — обязательная функция
В каждой рассчитанной строке мини-ШР кнопка «Расшифровка» рядом с изменением и удалением. Она связана с ID строки, не с её порядковым номером или названием. Нерассчитанная строка не показывает ложную детализацию.
Открывается модальное окно с заголовком должности, количеством единиц, долей, периодом бюджета. Закрытие кнопкой и Escape; прокрутка таблицы; управление фокусом без потери исходной формы.
Всегда 12 месячных строк + итог. Колонки:
1. Месяц.
2. Полная ЗП на руки / ед.
3. Полный gross / ед.
4. Полный НДФЛ / ед.
5. Полный gross накопительно / ед.
6. ЗП на руки объекта.
7. Gross объекта.
8. НДФЛ объекта.
9. СВ объекта без травматизма.
10. Травматизм объекта.
11. Премии объекта.
12. Итого объекта.
Полные колонки — для одной условной единицы; объектные — умножены на units и allocation. Все суммы в рублях с двумя знаками. Месяц вне работы строки — пояснение «доход не моделируется», не придуманная база. Месяц внутри работы, но вне бюджета — полная база видна, объектные суммы нулевые. Итог накопленной базы не суммировать по месяцам; объектные итоги совпадают с ШР и реестром.
Использовать monthlyTrace, полученную в том же расчётном цикле, не независимый пересчёт с другой логикой в UI. Изменение строки обновляет расшифровку; она не должна хранить устаревшую копию. После удаления связь не остаётся.
Подсказка: доля применяется после полного расчёта; премии вне налоговых баз; данные других выплат и реальные даты в этой модели отсутствуют.

# 17. Обзор, НДС, реестр и матрица
Dashboard: поступления; выплаты; ЧДП; начальный/конечный остаток; пиковый месяц выплат; расчётный НДС; ошибки; предупреждения; черновики. Месячная таблица: поступления, выплаты, ЧДП, накопленный остаток. Вне периода — явная отметка/пустое представление, не включать в итог. Таблица сообщений и раздельный ФОТ.
Расчётный НДС = выходной НДС доходов − входной НДС расходов, по месяцам и году. Разбивка входного по 22/10/7/5. «Без НДС» не попадает в ставки. Показатель не является автоматическим денежным платежом и не доказывает право на вычет/возмещение. Подписать ограничение. Ручную налоговую выплату можно вводить отдельно, без автоматического повторного НДС с самого налога.
Реестр: месяц, направление, статья, источник (Доход/Расход/Персонал), описание, сумма со знаком. По каждому пересчёту строится заново; не накапливать историю как новые платежи.
Матрица БДДС: код, название с отступом иерархии, 12 месяцев, итог. Поступления положительные, выплаты отрицательные. Группы для просмотра суммируются, но суммирование всех отображаемых строк для общего итога запрещено: это задвоит родителей и листья.
Инварианты: inflow = сумма положительных событий; outflow = модуль суммы отрицательных; net=inflow−outflow. По каждой статье/месяцу реестр совпадает с матрицей. Сумма месячных итогов совпадает с годовым/периодным итогом.

# 18. Сохранение и три индикатора
Кнопки: Новый бюджет; Открыть проект JSON; Сохранить проект JSON; Сохранить копию с датой; Восстановить из браузера; Проверить.
Обе кнопки сохранения выгружают одинаковый полный state в JSON, отличаются именем. Обычная: safeProject.json. Архивная: safeProject_копия_timestamp.json. Источник использует UTC timestamp для имени копии; для понятности допускается согласованный переход на локальное время, без заявления о перезаписи открытого файла.
Обычный download не подтверждает запись на диск: статус «Выгрузка запущена», имя и время, а не гарантированное «файл сохранён». Не обращаться к произвольным путям пользователя.
Три независимых индикатора с видимой точкой ss-dot:
- Сессия: зелёный — нет новых изменений; жёлтый — требуется выгрузка JSON.
- Браузер: зелёный — копия обновлена с временем; жёлтый — копии нет; красный — сбой хранения, предложение сохранить JSON.
- Файл: зелёный — открытая/выгруженная версия соответствует state; жёлтый — нет файла, состояние изменилось или выполнена миграция.
DOM панели — saveStatusPanel; точки должны быть реальными элементами, а не только CSS-классами контейнера. В тексте отображать актуальность; не полагаться только на цвет.
Сравнение с fileSnapshot выполняется по стабильному представлению исходного state; производные calc не входят в сравнение. Восстановление браузера сохраняет dirty, имя и время, не объявляет всё актуальным автоматически.
Ключи источника: bddsConstructorV6, bddsConstructorV6LastFile, bddsConstructorV6LastBrowser; fallback чтения bddsConstructorV5. При смене ключей реализовать перенос. Мета: name, at, snapshot, status, dirty.
localStorage — страховочная копия, JSON — основной файл. Ошибки записи и квоты не игнорировать. Повреждённую копию не перезаписывать пустым бюджетом автоматически; дать возможность получить исходное содержимое для восстановления. Перед заменой несохранённой работы и уходом со страницы — предупреждение.

# 19. Импорт, миграции и черновики
Алгоритм: прочитать → JSON.parse → проверить версию и структуру → глубокая копия → поддерживаемая миграция → изолированный previewCompute → показать отчёт → подтверждение → applyProject → обновить браузерную копию и метаданные.
previewCompute обязан восстановить прежние state/calc в finally даже при исключении. applyProject обеспечивает откат при ошибке применения/отрисовки. Нельзя менять current state или localStorage на этапе анализа кандидата.
Структурные ошибки (неизвестная версия, не-массивы, дубли/отсутствующие ID, неверные типы, небезопасная иерархия) — отказ. Проблемы редактируемого содержимого (например, отрицательная сумма, невыбранная допустимая статья) — отчёт и возможность открыть как черновик для исправления, без финального экспорта. Не позволять «черновику» обойти защиту от циклов и повреждённой структуры.
Поддержку версий 3/4 подтвердить реальными fixtures; иначе явно не заявлять. Версии 5/6 проверять обязательно.
Миграция allowManualFot=true и отсутствие fotMode: без строк ШР → manual_only; со строками ШР → mixed, запросить подтверждение обоих источников до применения. Отмена полностью сохраняет прежнюю работу. После миграции dirty=true, требуется новый JSON.
Открытие обычного JSON устанавливает имя открытого файла, а не имя предыдущей выгрузки. Браузерное восстановление допускает безопасные черновики, показывает ошибки для исправления. Экспорт с ошибками запрещён, сохранение JSON черновика разрешено.

# 20. Отчётный XLSX и CSV
Отчёт объекта — отдельная книга с восемью листами: Объект, Доходы, Расходы, Персонал, НДС, БДДС, Проверки, Материалы.
Объект: реквизиты, период, исходные единицы отображения, явное уточнение «денежные суммы файла в рублях», остатки, потоки, НДС, режим/параметры налогов, использованный год и источник, назначения статей персонала, дата формирования.
Доходы: раздел, статья, код, база, тариф, ставка, исходные месяцы, gross/НДС за месяц, итог за период, описание.
Расходы: тип, статья, код, номенклатура, единица, количество, цена, контрагент, договор, ставка, gross/НДС/net за месяц, исходные месяцы, итог за период, описание материала и комментарий.
Персонал: должность, график, единицы, доля, полная зарплата net/ед., gross/net/НДФЛ/СВ/травматизм/премии/итог за период. СВ отображать без повторного травматизма.
НДС и БДДС — 12 месячных колонок, итог; за пределами периода суммы не включаются. Проверки — статусы и сообщения. Материалы — точный materialRows как в CSV/HTML.
В XLSX числа хранить числами, коды — текстом; пользовательский текст — строкой, не формулой. Денежный формат #,##0.00. Совместимый OOXML; недопустим patternType=gray123, использовать допустимые стили. Проверка ZIP/CRC и чтение библиотекой не заменяют открытие в Excel.
Экспорт XLSX/CSV при ошибках блокируется. Предупреждения видны, не объявляются отсутствующими; для БИТ подтверждаются. JSON черновика сохраняется независимо от расчётных ошибок.
Расшифровка ШР в источнике — окно; отдельный экспорт этой расшифровки не обязателен.

# 21. БИТ: структура и незавершённая совместимость
Это критичный контракт, не произвольный Excel с похожими колонками. В исходнике встроены исходные части XLSX в EMBEDDED_BIT_TEMPLATE и точные строки EXACT_BIT_ROWS. Не генерировать заново упрощённую книгу через общий makeXlsx вместо шаблона.
Фактическая встроенная форма: листы «Данные бюджета» и «Лист1»; A1 пустая; A2 служебный заголовок; строка 3 пустая; A4 «Кодификатор», B4 «Статья оборотов», C4:N4 месяцы, O4 «Итого»; статьи 5–119; 115 строк статей. Это факты данного файла, не универсальное число строк БИТ.
Служебный заголовок: «Форма ввода бюджета {bitFormCode} от {bitFormDateTime} Выгружено: {текущая дата}».
bitFormCode — исходный идентификатор формы, формат текущей валидации 00-000XXX (три цифры). bitFormDateTime — исходная дата/время создания формы, ДД.ММ.ГГГГ ЧЧ:ММ:СС. Оба вводятся отдельно и сохраняются в JSON. Нельзя заменять их названием проекта, текущим временем или фиктивным 00-000111. Поля не являются дополнительными колонками бюджета.
Дата после «Выгружено» текущая, формируется жёстко с ведущими нулями, без locale-зависимой маски. Исходную дату проверять календарно, сохранять без подмены.
Порядок/названия/коды/нулевые строки берутся из точного шаблона, не из пользовательского активного дерева. Расходы по умолчанию отрицательные; bitNegSigns=false — суммы по модулю. bitGroupTotals меняет только числовые значения существующих групповых ячеек, не состав и порядок строк.
Сохранять имена ячеек, области видимости, стили, листы, связи и необходимые служебные части. При замене формул числами допускается удалить устаревшую calcChain и её ссылки согласованно. Не удалять другие части «ради упрощения».
Экспорт блокируется при неполном годе, расчётных ошибках, неверных реквизитах и ненулевых событиях по кодам вне шаблона. Не терять деньги молча. Названия статей в экспортной форме брать из шаблона даже при других внутренних подписях.

# 22. Известный блокер БИТ и требуемая диагностика
Встроенный XLSX содержит 1637 определённых имён, из них 14 с #REF!. Примеры и полный список — reference_contract.json/templateAudit. Идентификатор в части повреждённых имён: bcb2e5a094dc11ee8376005056a1be4c. Это нельзя считать корректным промышленным шаблоном.
Заказчик сообщает об исходной форме на 120 строк с ошибочной статьёй 706.102 «Расходы УК на содержание персонала клининга DEL», удалённой в варианте на 119 строк. Связь именно этой статьи с повреждённым GUID — гипотеза до получения нетронутого XLSX, не установленный факт.
Отчёт report.json: 1С 8.3.27.1688, форма документа бит_ФормаВводаБюджета; строка 915 «ЗнчСтр = Лист.Range(ИмяЭксель).Value»; исключение 0x800a03ec. Отчёт не содержит фактического ИмяЭксель. Он подтверждает сбой разрешения/чтения диапазона, но сам по себе не доказывает конкретную причину.
До производственной приёмки запросить: нетронутую проформу из того же документа БИТ, реально не загрузившийся XLSX, по возможности значение ИмяЭксель и имя листа в момент сбоя. Сопоставить имя→адрес→код статьи, найти отсутствующие и #REF!, проверить периодные префиксы и GUID.
Если БИТ ожидает удалённую строку, можно сохранить её технически с нулями в загрузочном шаблоне, не показывая для ввода управляющему. Не удалять именованные диапазоны и не восстанавливать строку догадками. Долгосрочно исправить форму в БИТ и получить новую исходную выгрузку.
Встроенные имена привязаны к 2027 и идентификаторам конкретной формы; замена видимых месяцев/кода не доказывает совместимость с другим годом/документом. Универсальность не заявлять без теста.
До устранения проблемы явно маркировать адаптер как непроверенный на реальной загрузке. Это не блокирует внутреннюю форму и JSON/отчёт объекта, но блокирует обещание «готово к промышленной загрузке».

# 23. Внутренняя архитектура и безопасность
Разделить ответственность: исходный state; чистое расчётное ядро; валидация; миграции; сохранение; render; экспорт. Можно сохранить имена функций исходника для минимального diff, но не размножать одноимённые определения и исправления в конце файла.
calc: issues[], events[], monthByArticle{}, monthIn[12], monthOut[12], inflow/outflow/net/closing/drafts, validIncomes/Expenses/Staff, staffRows, vatIncome/Expense/ExpenseByRate/Payable, fotStaffTotal, fotManualTotal, periodMonths, isFullYear.
Event в источнике: articleId, month, amount, source, description. Внутренние ссылки на запись допустимы, но скрыты. Не хранить независимую копию событий в JSON.
Экранировать пользовательский HTML/XML; избегать вставки ID в inline-JS без безопасного кодирования. Непроверенные строки не исполнять. JSON не должен менять прототипы и обработчики. Не делать fetch, аналитику или телеметрию в рабочем HTML. Полезно проверять отсутствие внешних URL-зависимостей автоматически.
При невалидной записи не оставлять половину её событий после исключения. Расчёт строки выполнять в буфере и применять атомарно. Ошибки профиля должны выдавать сообщение пользователю, а не останавливать весь интерфейс необработанным исключением.
Разработка может использовать инструменты среды Hermes, но требования не предполагают конкретных API, расширений или доступа к 1С у Афины. Изменения во внешних системах без отдельного поручения не выполнять.

# 24. Этапы исполнения для Афины
Этап A — инвентаризация: прочитать HTML целиком, отделить embedded XLSX от логики, сверить SHA, извлечь поля, функции, 115 статей; составить список as-is/дефектов. Не начинать с переписывания интерфейса.
Этап B — воспроизвести автономную форму и контракт JSON; добавить тесты чистых формул и миграций. Сначала получить совместимый результат baseline, отдельно держать исправления округления.
Этап C — реализовать все девять вкладок, CRUD, режимы ФОТ, 12-месячную трассу и окно; восстановление/индикацию; отчётный XLSX/CSV. Сравнить итоги.
Этап D — проверить embedded экспорт структурно и подготовить диагностику БИТ; заменить на нетронутый шаблон только после получения. Не маскировать внешний блокер.
Этап E — браузерная приёмка локального file://, сохранение/переоткрытие, отрицательные сценарии; журнал результатов.
Этап F — передача HTML, README, схемы, fixtures, отчёта; затем ограниченный пилот и внешняя приёмка БИТ.
На каждом этапе сообщать: изменённые блоки, проведённые тесты, что не проверено, риски. Не объявлять функцию реализованной только по наличию её имени. Не сокращать рабочий код ради длины ответа: писать файлы средствами среды, проверять их наличие и целостность.

# 25. Контрольные примеры и тест-план

T25 JSON download → изменить → reload браузера: восстановлены изменения и dirty; открыть сохранённый JSON — старые данные и правильное имя.
T26 Сбой localStorage → красный индикатор, работа продолжается, ручное сохранение доступно. Не заявлять гарантированное сохранение download.

# 26. Критерии завершения и отчёт о готовности
Внутренняя форма принята, когда проходят расчётные инварианты, CRUD, JSON round-trip, режимы/миграции, индикаторы, материалы, окно и отчётные выгрузки. Отдельно фиксируется режим округления и согласованные отличия от baseline.
БИТ-адаптер принят только после реальной обратной загрузки в нужный документ; открытие в Excel/openpyxl — необходимая, но недостаточная проверка.
Готовность представлять по уровням: «код проверен», «расчётные тесты», «браузер file://», «Excel-книга», «реальная БИТ-загрузка». Непроверенный уровень не обозначать зелёным автоматически.
Оригинал держать неизменяемым. Новые сборки именовать версионно; хранить SHA-256. Не удалять рабочие JSON заказчика. Сначала работать на тестовых копиях.

# 27. Входные материалы и вопросы, требующие решения заказчика
Обязательные входы: этот документ, исходный HTML и reference_contract.json. Дополнительно доступны legacy XLSX-шаблон и report.json ошибки загрузки; при отсутствии запросить их, не симулировать наличие.
До изменения методологии округления согласовать: оставляем исходный baseline ради воспроизведения или переходим на исправленные денежные инварианты с журналом отличий? Предлагается исправленный режим, но не скрытая замена.
Для БИТ запросить нетронутую форму на 120 строк из текущего документа и не загрузившийся Excel. Узнать, требуется ли технически сохранять 706.102 с нулевыми суммами.
Для реальных зарплат уточнить, являются ли месяцы строки периодом работы в УК или только участия в объекте. При разных периодах это отдельная доработка, не предположение алгоритма.
Афина не должна блокировать воспроизведение внутренней формы из-за отсутствия БИТ-доступа, но обязана оставить прозрачный внешний блокер интеграции.
