# А ты можешь ещё раз схематично отрисовать схему взаимодействия Little LLM + Cline Desktop + LLM model + Obsidian. Как это все планировалось что будет работать?

Да. Мы планировали не просто «Cline подключён к модели и читает Obsidian», а **управляемый гибридный контур**: Cline ведёт работу, Obsidian предоставляет долговременный контекст, маленькая локальная LLM помогает определить тип и сложность задачи, а отдельные правила безопасности решают, какие данные вообще можно направлять локальным или облачным моделям. После разрешения маршрута LiteLLM вызывает выбранную модель.

Важное различие: `Little LLM` — маленькая модель-помощник, а `LiteLLM` — шлюз вызова моделей. Это разные компоненты, хотя в прошлых обсуждениях их названия иногда смешивались.

## 1. Общая схема

Ниже — целевая архитектура, а не утверждение, что всё это уже настроено. В предыдущих обсуждениях мы отдельно фиксировали, что наличие политик в проекте ещё не означает наличие работающего Security Gateway и маршрутизации.

```text
                         АНДРЕЙ
               Задача / вопрос / утверждение
                            │
                            ▼
                 ┌──────────────────────┐
                 │    CLINE DESKTOP     │
                 │                      │
                 │ Интерфейс работы     │
                 │ Планирование         │
                 │ Rules и инструкции   │
                 │ Вызовы инструментов  │
                 └──────────┬───────────┘
                            │
                  Запрос нужного контекста
                            │
                            ▼
         ┌────────────────────────────────────────┐
         │ ЛОКАЛЬНЫЙ КОНТРОЛЬ ДОСТУПА К ДАННЫМ   │
         │                                        │
         │ Можно ли читать этот путь?             │
         │ Какие файлы нужны для задачи?          │
         │ Нет ли секретов / запрещённых данных? │
         └─────────┬──────────────────┬───────────┘
                   │                  │
                   ▼                  ▼
        ┌──────────────────┐  ┌──────────────────┐
        │ OBSIDIAN VAULT   │  │ GIT-ПРОЕКТ FREYA │
        │                  │  │                  │
        │ Знания           │  │ Код, тесты       │
        │ Исследования     │  │ Specs, ADR       │
        │ Решения          │  │ .clinerules      │
        │ Контекст проекта │  │ Project state    │
        └─────────┬────────┘  └─────────┬────────┘
                  │                    │
                  └──────────┬─────────┘
                             │
                    Отобранный контекст
                             ▼
         ┌────────────────────────────────────────┐
         │       PREFLIGHT SECURITY GATE          │
         │                                        │
         │ Проверка полного исходящего запроса:   │
         │ задача + история + файлы + tool results│
         │                                        │
         │ Black → BLOCK                          │
         │ Red   → LOCAL ONLY                     │
         │ Yellow→ LOCAL / проверенная копия      │
         │ Green → разрешён LOCAL или CLOUD       │
         └───────────────────┬────────────────────┘
                             │
                 Только допустимый контекст
                             ▼
         ┌────────────────────────────────────────┐
         │ LITTLE LLM — маленькая локальная модель│
         │                                        │
         │ Помогает определить:                   │
         │ • тип задачи и роль                    │
         │ • сложность                            │
         │ • подходящую модель                    │
         │ • необходимость эскалации              │
         │                                        │
         │ Не может отменить запрет безопасности  │
         └───────────────────┬────────────────────┘
                             │
                      Рекомендация маршрута
                             ▼
         ┌────────────────────────────────────────┐
         │       ДЕТЕРМИНИРОВАННАЯ ПОЛИТИКА        │
         │                                        │
         │ Проверить разрешённый маршрут, бюджет, │
         │ доступность модели и ограничения данных│
         └───────────────────┬────────────────────┘
                             │
                             ▼
                 ┌──────────────────────┐
                 │   LITELLM GATEWAY    │
                 │ Единая точка вызова  │
                 │ разрешённых моделей │
                 └──────────┬───────────┘
                            │
                ┌───────────┴────────────┐
                ▼                        ▼
     ┌────────────────────┐   ┌─────────────────────┐
     │ ЛОКАЛЬНЫЕ МОДЕЛИ  │   │ ОБЛАЧНЫЕ МОДЕЛИ    │
     │                    │   │ Через OpenRouter / │
     │ local-small        │   │ разрешённый API    │
     │ local-main         │   │                    │
     │                    │   │ Только разрешённый │
     │ Разрешённый        │   │ для облака контекст│
     │ локальный контекст │   │                    │
     └─────────┬──────────┘   └──────────┬──────────┘
               │                        │
               └────────────┬───────────┘
                            ▼
                    Ответ модели в Cline
                            │
                 Предложение следующего действия
                            ▼
              Проверка прав / ваше подтверждение
                            │
                  Инструменты → тесты → результат
```

Основа этой схемы — ранее обсуждённое разделение: агент управляет рабочим процессом, Security Gate ограничивает обработку и передачу данных, LiteLLM маршрутизирует только уже разрешённые вызовы. Маленькая модель не должна единолично разрешать отправку данных наружу.

## 2. За что отвечает каждый компонент

| Компонент | Его роль | Чего он не должен делать |
| :-- | :-- | :-- |
| Cline Desktop | Принимать задачу, читать правила, планировать, вызывать инструменты, предлагать и выполнять согласованные изменения | Самостоятельно отменять ограничения безопасности или утверждать финансовые факты |
| Obsidian | Хранить исследования, решения, методологию, обзоры и отобранный контекст | Заменять БД Freya, вычислительный движок или Git |
| Little LLM | Помогать классифицировать задачу, выбирать роль и оценивать необходимую мощность модели | Быть единственным судьёй конфиденциальности и разрешать облачный маршрут вопреки политике |
| Security Gate | Проверять данные, пути и допустимость исходящей передачи | Полагаться только на ответ маленькой модели |
| LiteLLM | Вызывать выбранную локальную или облачную модель по разрешённому маршруту | Отправлять Red в облако при недоступности локальной модели |
| Основная LLM | Решать содержательную задачу: анализ, архитектура, код, review | Считать доступ к данным разрешением на любые действия |
| Вы | Утверждать существенные решения, запись, публикацию и рискованные операции | Вручную повторять весь контекст проекта в каждом новом чате |

Такое распределение ролей соответствует нашей ранее обсуждавшейся модели личной AI-лаборатории.[^1]

## 3. Как Little LLM выбирает модель

Логика задумывалась в два независимых шага:

```text
Сначала: где эти данные разрешено обрабатывать?
Затем: какая из разрешённых моделей лучше решит задачу?
```

Например:


| Задача | Ограничение данных | Предлагаемый маршрут |
| :-- | :-- | :-- |
| Составить архитектуру публичного модуля Freya на безопасном контексте | Green | Сильная облачная модель для роли `/arh` |
| Исправить небольшую функцию на тестовых данных | Green | Локальная модель, если доступна; иначе разрешённая облачная |
| Проанализировать реальный личный портфель | Red | Только разрешённый локальный контур |
| Подготовить черновик по внутренним заметкам | Yellow | Локально; для облака сначала отдельная проверенная копия |
| В контексте обнаружен API-токен | Black | Блокировка затронутого запроса, уведомление владельца |

Для разработки Freya мы обсуждали последовательность:

```text
Архитектор
→ разработчик
→ инструменты и тесты
→ проверка качества
→ подготовка Git-изменений
→ ваше утверждение
```

При этом роли `/arh`, `/dev`, `/qa`, `/git` — это назначения работы, а не обязательные отдельные автономные агенты. Одна модель или один Cline-сеанс может выполнять их последовательно по разным инструкциям.

### Если локальной мощности недостаточно

Мы хотели сохранить возможность облачного выполнения, пока локальное оборудование ещё не готово. Но это правило действует только для данных, которым разрешено покидать локальный контур.

```text
Green + локальная модель недоступна
→ разрешённый облачный маршрут.

Yellow + локальная модель недоступна
→ подготовить и проверить безопасную копию
  либо отложить обработку.

Red + локальная модель недоступна
→ остановить задачу / использовать разрешённые локальные инструменты.
  Не переключать в облако.

Black
→ не передавать ни локальной, ни облачной LLM.
```


## 4. Как Obsidian становится «памятью»

Мы не планировали загружать весь Vault в модель при каждом запросе.

Предполагалась адресная загрузка:

```text
Задача по Freya
    │
    ▼
Карта проекта / MOC
    │
    ▼
Релевантные заметки и принятые решения
    │
    ▼
Минимальная подборка контекста
    │
    ▼
Проверка безопасности
    │
    ▼
Выбранная модель
```

А состояние разработки восстанавливается прежде всего по Git:

```text
AGENTS.md
+ .clinerules/
+ PROJECT_STATE
+ актуальные specs / ADR
+ текущая задача
```

Obsidian дополняет это исследованиями и предметным контекстом, но не создаёт вторую конкурирующую версию технических требований. Именно такое разделение было заложено в активном интеграционном draft.[^1]

### Обратный поток результатов

Для результатов Freya:

```text
Freya
→ локальный staging
→ validation
→ dry-run
→ ваше подтверждение
→ новый generated-отчёт в Obsidian
```

Для заметки, подготовленной Cline:

```text
Cline
→ предложенный текст и путь
→ ваше подтверждение
→ 07-Agent-Drafts/Cline/
→ ваш review
→ при необходимости утверждённая заметка
```

Generated-отчёты Freya и черновики Cline имеют разных владельцев и не должны смешиваться. Для первого MVP мы дополнительно решили не перезаписывать существующие файлы.[^1]

## 5. Важное уточнение схемы безопасности

Проверка должна происходить не только один раз на входе пользователя, но и после получения нового контекста.

Например:

```text
Безопасная задача Green
→ Cline читает разрешённый файл
→ в результате инструмента оказались Red-данные
→ следующий запрос нельзя отправлять в облачную модель.
```

В нашей целевой схеме gate охватывает задачу, файлы, результаты инструментов и RAG-контекст. Поэтому модель не получает новые данные до проверки допустимости маршрута.

И ещё одно: `.clinerules` — инструкции агенту, а не техническая изоляция. Чтобы эта схема действительно защищала данные, нельзя оставлять обходные пути через прямые облачные вызовы, инструменты или отправку файлов. На этапе реализации это нужно проверять отдельно, а не считать обеспеченным одним файлом правил.

## 6. Что мы собирались внедрять сначала

Не весь этот контур сразу. Последовательность была такой:

1. Правила, классификация данных и ручной выбор роли/модели.
2. Один безопасный Green-сценарий на тестовых данных.
3. Проверяемый экспорт Freya в Obsidian.
4. LiteLLM и разрешённые псевдонимы моделей.
5. Локальная Little LLM как помощник маршрутизации.
6. Техническое применение Security Gate и ограничений передачи данных.
7. Только после проверки защиты — работа с Yellow/Red-контекстом.

Это сохраняет исходный замысел: Cline — ваше рабочее место, Obsidian — долговременная память, Little LLM — диспетчер-помощник, основная LLM — исполнитель содержательной задачи, а безопасность определяется отдельной политикой, которую ни одна модель не может отменить.
