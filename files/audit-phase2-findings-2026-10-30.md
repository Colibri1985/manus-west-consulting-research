## 1. Подтверждённые защитные меры

У gateway и dashboard:

- CapEff=0;
- privileged=false;
- cap_drop=[ALL], добавленные capabilities не заданы;
- readonly_rootfs=true;

- host PID namespace не используется;

Это реальные защитные меры. Они не являются доказательством общей безопасности или полной изоляции сети и данных.

Проверенные config.yaml, auth.json, state.db и cron/jobs.json имеют owner 10000 и mode 0600. Это не разрешает читать их обычным другим UID по данным mode-битам. У root, процессов с тем же UID и иных разрешённых путей может оставаться доступ; ACL и все внешние интерфейсы отдельно не проверялись.

Каталоги memories, skills, sessions, cron и logs имеют 0755. Это не равнозначно открытости содержимого файлов: важны права конкретных файлов, права родителей и доступ к mount. Массовый chmod не предлагается.

## 2. Сеть — важный пробел, но не доказанная открытость извне

У gateway и dashboard host_network=true. По официальной документации Docker host-mode использует сетевое пространство хоста; обычные опубликованные Docker-порты при этом не характеризуют доступность приложения.

Поэтому published_ports=[] нельзя читать как «ничего не слушает» или «dashboard закрыт от интернета».

Нужно проверить реальные TCP listeners, привязку loopback/wildcard и затем, если требуется, firewall/внешнюю достижимость. Host-mode может быть намеренным решением для связи с executor; менять его без проверки соединений нельзя.

У executor host_network=false. SSH-порт контейнера опубликован на host port 22222 только с loopback-привязкой. Этот факт не заменяет проверку всех сетей, маршрутов, SSH-политик и firewall.

## 3. Общий доступ к данным

Gateway и dashboard имеют один и тот же родительский bind /srv/hermes-agent/telegram-data -> /var/lib/hermes, с RW-доступом, и один числовой UID 10000.

Между ними нет независимой файловой границы для этого общего профиля: 0600 не разделяет два процесса одного UID. Для двух интерфейсов одной Афины это может быть намеренным. Это не следует представлять как изоляцию профилей/проектов или как доказанное нарушение.

У executor RW-доступ к общей workspace и домашний volume. Кэш входящих документов примонтирован RO. Полный parent home gateway в executor не примонтирован по показанному списку. Это соответствует наблюдению, что executor не видит gateway state.db/config/memories по их обычным путям.

### Проверяемая гипотеза о рассинхронизации конфига

В dashboard config.yaml дополнительно примонтирован отдельным RO file bind, а в gateway виден через родительскую директорию. При атомарной замене файла на хосте file bind может продолжить ссылаться на прежний объект.

Это пока гипотеза, не установленный факт. Нужны сравнение байтов/метаданных двух видимых config.yaml и разрешённых полей без вывода содержимого. Перезапуск dashboard вслепую не предлагается.

## 4. Ограничения ресурсов

У gateway и dashboard не задан собственный Docker memory limit, pids_limit=null. Это пробел в наблюдаемых лимитах контейнеров, но не доказательство отсутствия всех ограничений хоста/родительских cgroups.

У executor заданы memory limit и pids_limit=256. Корневая файловая система executor доступна на запись, PID 1 и административный docker-exec probe имеют UID 0 и стандартный набор capabilities. При этом реальные команды Афины по SSH выполняются под UID 10000 с CapEff=0; no-new-privileges и seccomp наблюдаются.

Нельзя объявить root PID 1 сам по себе ошибкой или менять --user без разбора запуска SSH. Равным образом нельзя объявить полную безопасность executor по одному непривилегированному SSH-процессу.
